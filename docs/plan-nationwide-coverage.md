# 全国接入排期计划（目标：337 城全覆盖）

> 目标口径：**333 个地级行政区**（293 地级市 + 7 地区 + 30 自治州 + 3 盟，民政部 2024 年底口径）+ **4 个直辖市** = **337 城**。
> 当前进度：**202 城（59.9%）** = 直辖市 4（北京/上海/天津/重庆）+ 广东 21 + 四川 21 + 山东 16 + 辽宁 14 + 吉林 9 + 黑龙江 13 + 江苏 13 + 浙江 11 + 河南 17 + 湖北 13 + 湖南 14 + 安徽 16 + 福建 9 + 江西 11。
> 剩余：**135 城**。

## 一、排期口径说明

本计划用**批次顺序 + 验收门 + 工作量（城市数）**表达排期，不用日历天数：单个省份的实际耗时几乎完全由「该省各市是否公开医保费率与公积金基数」决定（有的市根本不发文，只能标 `warn` 兜底），给出具体日期会误导。若需要日历排期，建议先跑完第 0 波，用实测单省耗时回填后续各波。

## 二、四个关键杠杆（决定边际成本很低）

1. **五险基数多为省级统一**：山东（鲁人社字〔2026〕75号，含医保）、四川、辽宁已验证「一省一个基数区间 + 文号」即可覆盖全省所有市。
2. **每市增量数据只有 3 类**：① 医保单位费率（是否含生育）② 公积金基数上下限 + 文号 ③ 最低工资档（决定公积金下限与个税租金档 1500/1100/800）。剩下全部从省级继承。
3. **工厂函数无需改动**：`CIU()`（五险统一基数型）+ `opt` 浅覆盖已能表达全部形态；基数与省市不一致时用 `opt.med` 单独覆盖（四川攀枝花/泸州等已验证）。
4. **调研可并行**：`general_purpose_task` 子代理具备联网能力，可按「1 省 1 子代理」并行取数（本轮辽宁/吉林/黑龙江/山东已实测可行）。

**断言数影响**：`test-calc.js` 第 8 节对每城自动生成 18 条结构断言 → 每新增 1 城断言数 **+18**，另加每省 ≥3 条参数抽查。337 城全部接入后断言数预计 ≈ 202 城 3950 + 135×18 + 抽查 ≈ **6500 上下**。

## 四、每省标准作业流程（SOP，固定 8 步）

1. **省级调研**（联网，1 次）：五险基数上下限 + 文号；养老/失业/工伤/医保/生育费率；判定是否省级统一。
2. **市级调研**（并行子代理，1 市代理或多市打包）：各市医保单位费率、公积金上下限 + 文号、最低工资档。
3. **落盘**：`docs/policy-<省拼音>-<年度>.md`，附来源文号与**缺口清单**；查不到的写「未找到」。
4. **写 CITIES**：`CIU(名称, {min,max}, {费率...}, {hf min,max}, {region:"省名", dataYear, rent, note, warn?})`；基数与省市不一致时用 `opt.med` 覆盖。
5. **文档涟漪五件套**（见下表，缺一即被 check-sync 拦下）。
6. **测试**：`test-calc.js` 增该省 ≥3 条参数抽查断言 + 更新「城市总数」。
7. **五连验证**：`sync.js` → `test-calc.js` → `check-dom.js` → `check-sync.js` → `test-export.js`，必须全绿。
8. **交付**：`commit` + `push`（main 自动触发 Cloudflare Pages）→ 抓取线上页面核验新增城市渲染。

## 五、范围边界与命名规范（先定规则，避免后续返工）

1. **只做地级行政区 + 直辖市**。省直管县级市（河南济源、湖北仙桃/潜江/天门、海南儋州以外的县级市、新疆兵团市等）不在 337 口径内，列为「可选扩展」，需要时再单独评估。
2. **自治州 / 地区 / 盟 用惯用简称**：延边、大兴安岭、甘孜、凉山、阿坝（已在用），新接入沿用 2-3 字简称，`name` 不加「自治州/地区/盟」后缀，`region` 用省/自治区名。
3. **计划单列市（大连、青岛、宁波、厦门、深圳）社保独立经办**，必须按市级文件单独调研，禁止套省级口径（`CI()`/`CIU()` 选择也据此判断）。
4. **直辖市**统一归入 `region:"直辖市"` 分组（京沪渝已如此，天津同）。
5. **个税租金档**：直辖市/省会/计划单列市 = 1500；其余按市辖区户籍人口 >100 万 = 1100、≤100 万 = 800。无法确认户籍人口时先按 1100 并在 `note` 标注待核实。
6. **工伤一律按一类行业基准费率**写入（个人不缴，不影响到手工资，仅影响单位侧展示）。

## 六、质量门与兜底策略

| 门 | 内容 | 不过的处理 |
|---|---|---|
| G1 镜像 | `sync.js` 后 A 段必须一致 | 补跑 sync |
| G2 文档覆盖 | check-sync B：每城 医保/公积金 上下限均在 AGENTS.md + SKILL.md 可检索 | 补文档 |
| G3 无陈旧表述 | check-sync C：城市清单类措辞不得残留旧城市数 | 修文案 |
| G4 断言一致 | check-sync D：文档「N 项断言」= test-calc 实际输出 | 改文档 |
| G5 结构完整 | test-calc 第 8 节：字段齐全、min≤max、`hfRateMax∈[5,12]` | 修 CITIES |

**兜底原则（不阻塞推进）**：任何一项数据联网查不到 →（a）`CITIES` 标 `warn:true`（橙框「数据待确认」）；（b）`note` 写明「未找到」与暂用口径；（c）写入 `docs/policy-*.md` 缺口清单；（d）纳入三级时效检查点（1 月医保 / 7 月养老公积金 / 限期费率到期）与「补齐待办」。**绝不编造数字**。

## 八、主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 医保费率/公积金基数普遍不公开 | 大量城市带 `warn`，可信度参差 | 明确标注而非留空；逐年检查点补核；页面橙框已提示「仅供参考」 |
| 中间年份省级文件未发布（如黑龙江 2026 年度基数） | 只能用旧年度 | `dataYear` 区分年度；`note` 写明待公布 |
| 省级与市级基数不一致的省（辽宁/吉林/黑龙江已见） | 套省级会算错 | 用 `opt.med` 覆盖；每省调研时专门确认「医疗基数是否单独口径」 |
| 命名/分组不统一导致 UI 混乱 | 后续返工 | 第五节规则先行，第 4 波做全量审计 |
| 断言数与城市数涟漪漏改 | CI 守卫报错 | 四、五节的固定清单 + check-sync C/D 双拦截 |
| 全国覆盖率提升后页面体积变大 | 单文件 HTML 加载变慢 | 337 城约新增 20KB 量级 JS，仍在可接受范围；若超预期再评估按需加载 |
